# Epsilon Billing (Payments Epsilon)

Billing tracker for Epsilon Electrical & Electronic Contracting (Kuwait). Two ledgers —
**Receiving** (sold, money in) and **Sending** (bought, money out) — each showing bill,
down payment, paid and left to pay. Full user-facing docs are in `README.md`.

## Architecture
- No server, no build step. Static files in `public/` talk directly to Supabase from the browser.
- `public/index.html` — layout. `public/styles.css` — light/dark theme, IBM Plex, orange `#ea7a00`.
- `public/app.js` — all logic (~3950 lines, vanilla JS, `window.supabase` client). `CONFIG` is at the top (Supabase URL, publishable key, email domain).
- `supabase/migrations/` — SQL for schema changes, so they can be reviewed in a diff. Its `README.md` maps each file to the migrations it was applied as, and warns that the 22 baseline migrations live only in Supabase's history, so the folder cannot rebuild the database from empty.
- Logins are username-based: username is mapped to `<username>@<CONFIG.emailDomain>` for Supabase Auth. User management goes through an edge function (`callUsersFn`).
- Permissions (see/edit/manage users) are enforced by database RLS, not just hidden in the UI.

## Behaviour to preserve
- Currency decimals: KWD/BHD/OMR/JOD/TND/LYD = 3, everything else = 2 (`CUR_DEC`), so "zero left" means exactly zero.
- Excel/CSV import auto-detects headings in any order, skips title rows and a trailing Total row, shows a column-mapping preview before import. The invoice format is **Invoice Number, Supplier Name, Supplier Number, Supplier Details, Brand, Description, Unit Price, Model (SKU), Quantity**. The first four repeat on every row and describe the file, not the item: `sheetInfo` takes the value used on the most rows. Supplier Details is the supplier own phone/address/email, never Epsilon. Supplier Number is their account/ref code. Headings overlap ("Supplier Details" contains "details"), so `mapRow` scores every field/column pair and settles the strongest claim first, one field per column. Files in the older layout (no invoice/supplier columns) still import.
- Invoice upload (PDF/Excel/CSV) extracts invoice number, date, currency and total; prefers "Total after discount". An uploaded invoice's total replaces the item-list total as the bill; mismatch shows an amber warning. Newest invoice wins, older ones are kept. Files are private, opened via 10-minute signed links.
- Record shipment (Shipments page) opens on an upload box only. The file is read, the order is matched by invoice number (+60 for order reference, +10 per item model found), arrived quantities are read from the lines carrying each model, and the result shows "settles to zero" or "N items left" before saving. A full delivery books exactly the outstanding value so the account lands on zero; a partial one books the value share of the items that arrived. `shipments.items` (jsonb `[{key, model, qty}]`) remembers which units arrived so later shipments know what is left. Logic: `rankOrders` / `readArrivals` / `shipmentOutcome` in `public/app.js`.
- Supplier name from an invoice: `extractSupplierName` takes a labelled "Supplier:" line, else the first company-looking header line (skipping Epsilon's own "To/Bill to" block, titles, addresses, non-Latin twins). `matchParty` maps it to an existing account tolerant of legal suffixes and small typos (e.g. "GUANGZHOU DSPPA AUDIO CO., LTD." → account "Guanghzow"), because the database links a deal to an account only on an exact lowercase name and otherwise creates a new account. Used on New purchase (accepts a PDF) and as a +40 nudge when matching a shipment invoice to an order.
- A sheet imports more than items: `saveSheetInfo` writes the invoice number to `invoices` for the order and the supplier's contact details to `parties.details`. It never overwrites details already on file - the first invoice from a new supplier is what opens their account - so corrections go through **Edit details** on the account page (`partyDialog`).
- **One supplier holds one supplier number, ever, and the app assigns it.** `parties.supplier_no` is the account number *we* give a supplier, not a code they print: none of the three real invoices carries one, so left to hand entry the field stays blank and the one-number rule has nothing enforcing it - and a second number quietly splits a supplier's balance across two accounts. So `ensure_supplier_no(party, claim)` settles it, and is idempotent: a number already on file always wins, a number the sheet claims is taken up only by an account that has none, and a claim already belonging to someone else is refused and a fresh `SUP-` generated. A partial unique index on `lower(btrim(supplier_no))` is the backstop. The 11 existing accounts adopted their phase 1 `sup_code` as this number rather than being reissued. Decided with the owner 2026-11-01, who asked for the app to own it rather than typing it.
- **SUPERSEDED on 2026-11-07 by the "built from the name" rule below** - this shape now applies only to accounts numbered before that date, which keep it (Guanghzow still holds `SUP0004`). Kept because it explains those numbers: **an account number is three letters then four digits** - `SUP0012`, `CUS0001` - set by the owner on 2026-11-01. `next_party_code()` and `peek_party_code()` both emit that shape and `next_party_code()` *raises* past 9999 rather than widening to five digits, which would leave two formats in the ledger. The 11 existing accounts were **reformatted, not renumbered** (`SUP-000003` → `SUP0003`): the digits carry across, so an account keeps the number it already had, which is what the one-supplier-one-number rule requires.
- **"Fully paid" on New purchase** ticks the whole bill into the down payment and locks the box. It recomputes `deal_summary`'s arithmetic client-side - each line rounded to 4 decimals, discount off the subtotal, result rounded to the currency's decimals (`billNow`) - because landing on *exactly* zero left is the point; a figure typed by hand leaves fils owing. The amount follows the item list and the discount while the box is ticked, and the submit recomputes it again rather than trusting what is in the field.
- **The rule is now one ACCOUNT, one number - customers included - and a trigger issues it (2026-11-07).** `ensure_party_no(party, claim)` generalises `ensure_supplier_no` to either kind and keeps its three rules exactly: a number on file always wins, a claimed number is taken up only by an account that has none, and a claim belonging to someone else is refused and a fresh code generated. A customer's number lives in **`supplier_no` too**, not a second column: `supplier_no` already means "the account number we give them", the partial unique index on `lower(btrim(supplier_no))` is already the backstop against a balance splitting in two, and a `customer_no` column would need a second index, a second rule, and would have nothing to say about an account whose kind is `both`. `sup_code` / `cus_code` are filled to match. A `parties_autonumber` **before-insert trigger** assigns the code, so an account comes out numbered whatever opened it - the Accounts screen, an invoice import, or the deal-to-account link - while an insert that already carries a number keeps it, which is the seam a deliberate claim still goes through. **The side effect to remember:** because no new account is ever unnumbered now, `ensure_supplier_no`'s "a number the sheet claims is taken up by an account that has none" branch no longer fires for a newly created account - to honour a sheet's claim it has to be passed *on the insert*. A `parties_touch` trigger stamps `updated_at` / `updated_by`.
- **An account number is now BUILT FROM THE NAME: three letters, a hyphen, then the first number not used under those letters** - `MNC-0038`, `BSS-0001`, `KHT-0001`. Asked for by the owner on 2026-11-07, because it is how they have always numbered accounts by hand: "Mindware Computers" is `MNC-0037` on their own books. `party_code_prefix(name)` takes **three or more significant words → their initials** (Bosch Security Systems FZE → `BSS`, the legal suffix dropped), **two words → first letter, the next CONSONANT of that first word, then the second word's initial** (Mindware Computers → `MNC`, which is what reproduces the owner's own code), and **one word → its first three letters** (Guanghzow → `GUA`); a name with no Latin letters falls back to `ACC`. `party_code_for(name)` then takes the **highest number already issued under that prefix plus one**, so Mindware's neighbour is `MNC-0038` and never `MNC-0001` - numbers are never reused, which is what makes an account number permanent. It raises past 9999 rather than widening to five digits, for the same reason the old shape did. **There is no sequence behind this, so there is no `peek` twin:** the code is computed from the rows that exist rather than drawn from `doc_sequences`, so the New account form can preview it on every keystroke and abandoning the form costs nothing. The unique index on `lower(btrim(supplier_no))` is the backstop if two inserts race. **Accounts numbered before this keep what they hold** - renumbering is retroactive across every invoice already recorded, so it is never automatic.
- The number is editable in two places - **Edit details** on the account page (`partyDialog`) and the **Supplier number** field on New purchase - and both behave the same way: clearing the box keeps the number on file rather than wiping it, because an account must never end up unnumbered, and typing a number another account holds is caught and answered with *whose* it is, not the raw constraint name.
- **Typing a number on New purchase renumbers the account, not the invoice, and says so first.** The field is filled from the settled number; changing it opens a confirmation spelling out the consequence ("changes it on every invoice already recorded against them and on every invoice after this one"), because the number lives on `parties`, so the change is retroactive by nature and a silent edit would look like it applied only to the order being created. Only then does the save call `api.setSupplierNo` - `ensure_supplier_no` deliberately will *not* renumber, since keeping what is on file is the whole point of it.
- The import preview shows the supplier number it settled on, with the reason: existing account reused, number taken from the sheet, set by hand, or - for a supplier not yet on file - the number they are about to get, read from `peek_party_code()`. That function reads `doc_sequences` **without advancing it**: calling the real generator for a preview would burn a code every time an import was opened and abandoned, and codes are never reused, so each cancelled preview would leave a permanent hole. It is a prediction, not a reservation - `next_party_code()` still decides on save. Where a sheet disagrees with the account, an amber warning says which number was kept. **Supplier Number is not the SKU**: `Model (SKU)` identifies the part and changes every row; Supplier Number identifies the company and repeats down the whole file. An invoice row is only written when the sheet priced it, because a recorded total becomes the bill and a zero would flatten the order.
- **The Accounts screen opens an account outright, and lists every account (2026-11-07).** `partyDialog(null, done)` is the New account form; `partyDialog(p, done)` edits one. It carries the fields of the owner's legacy "Account Receivable" screen that have something behind them here: number, kind, name, **name (Arabic)**, contact person, mobile, telephone, e-mail, address, CR number, credit limit, currency, payment terms, active, details, remark, created/updated stamps. Dropped on purpose, as fields that would save nowhere: Category 1/2, Date of Birth, Any Price, Sales Flag, Branch 1/2, Alternate Print / SPCL / Print[1/0], Salesman, Pager, Fax, Res.Tel; P.O. Box folds into `address`. **"GL Account" is shown read-only** because `posting_templates` decides the control account, not the party row - a writable box there would be a lie. The list is a grid (code / name / Arabic name / kind / mobile / telephone / orders / balance) with one live search box over all of those, replacing the legacy radio buttons and Find First / Find Next. It shows **every** account, not only ones with a live order, because an account opened from this screen has no orders by definition and the old filter would have hidden it the instant it was created. The dialog sends `''` or `0` for an empty `notes` / `tax_id` / `credit_limit` / `payment_terms_days` box - all four are `not null` on `parties` - and null only for `details` / `default_currency`, the two that are nullable.
- **New sale and New purchase offer the accounts already on file as you type** (`attachPartyPicker`), because the database links a deal to an account on an **exact lowercase name** and otherwise opens a new one - so a name one character off splits that party's balance across two accounts. Ranking is `partyScore`, the tolerant matcher the invoice import uses, widened with plain substring and account-number hits: `partyScore` alone wants a distinctive token of five characters before it scores at all, so two or three typed letters would otherwise match nothing. Accounts of the form's own kind sort first; picking a supplier also settles their number into the field through `settleSupplierNo`, the same path an imported invoice uses. Typing after picking clears the pick, so "they chose this account" stays distinguishable from "they typed something that resembles it". Reuses the existing `.suggest` type-ahead styles.
- **The item preview scrolls sideways; it must never be allowed to just fit.** `.preview-scroll` has a 1040px floor and `white-space: nowrap` on every cell but Description. A table that merely fits its container has nothing for `overflow-x` to do, so instead of scrolling it crushes every column - supplier names wrap onto two lines and Amount ends up under the vertical scrollbar with no way to reach it. That is what a 860px floor did on the full-width New purchase page, whose content column is about that wide. Separately, `.modal-body > *` and `.card-body > *` need `min-width: 0`, or a grid/flex child's `min-width: auto` stretches the container instead of letting `.table-scroll` scroll.
- Shipments read a spreadsheet structurally (`sheetHeaderInfo`) rather than by regex: flattening a sheet puts headings side by side ("Invoice Number Supplier Name"), which a loose "invoice no:" pattern reads as the supplier. `extractFromLines` tries labels most-explicit-first, requires a digit, rejects dates and heading words, and falls back to the line under a heading row ("PI Number / Date" then "SOR-03180 08-Oct-2026").
- Stock lists, per item, the supplier, their invoice number and the order it came in on. `stock_levels` keys an item by `lower(model, else description)` as `stock_key`; `viewStock` keys the order lines the same way and joins. It reads those names from purchase orders only — the view own `party_names` mixes in the customers an item was sold to. An item shows "—" until an invoice number is recorded against its order.
- The sidebar shows tab names only; the old sub-labels ("sold", "purchases", "receipts", "all orders", "on hand", "UIDs") were removed 2026-10-28 at the owner request.
- First run shows "Create owner account" (only one owner can be created this way); afterwards it is a normal login.
- **A reversed journal stays in `general_ledger` — and in every balance.** Any view summing `journal_lines` filters `status in ('posted','reversed')` on purpose: `reversed` means "corrected", not "never happened", and the linked mirror journal is what cancels it, so the pair nets to zero. Filtering to `posted` alone removes the original and leaves the mirror standing, which shows every corrected transaction as its own opposite. This was a real bug on 2026-10-29 in `general_ledger` — **and it came back on 2026-11-02** in phase 4's `customer_advances`, `supplier_advances` and `bank_balances`, where the acceptance test caught a reversed KWD 400 advance reporting as −400. Fixed in `erp_phase4_reversed_journals_stay_in_balances`. It is the easiest mistake to repeat in this schema: check it in every new view that sums the ledger.
- Three rules live in the database, not in `app.js`, and must stay there: debit must equal credit at the moment of posting; a posted journal can only ever move to `reversed` (never edited, never deleted); and a unique index on `(source_table, source_id, event)` where `status = 'posted'` means one event posts once, so a retry or double-click cannot double-post.
- **Only a draft is writable from the client.** The RLS policies on `goods_receipts`, `goods_receipt_lines`, `landed_costs`, `landed_cost_lines`, `deliveries`, `delivery_lines`, `sales_invoices`, `sales_invoice_lines`, `credit_notes` and `credit_note_lines` all carry `status = 'draft'`, so a posted document cannot be edited or deleted from the browser — it moves on only through `post_goods_receipt` / `cancel_goods_receipt` / `post_landed_cost` / `post_delivery` / `cancel_delivery` / `post_sales_invoice` / `cancel_sales_invoice` / `post_credit_note`, which are `security definer` and so still do every legitimate transition. Each table originally had one `for all using (can_edit())` policy, which let a posted receipt be deleted outright while its `stock_moves`, its blended `item_costs` average and its posted journal all stayed behind — stock and the ledger claiming goods with no document under them, and `cancel_goods_receipt()` then unable to undo it. Caught 2026-10-29. An UPDATE that fails `using` affects zero rows rather than raising, so a posted row simply does not respond.
- **The sales path keeps three things apart, and they must stay apart.** Approving and reserving only *promise* goods — `qty_reserved` (on `item_costs` for the warehouse total, on `deal_items` for each order's share) never touches `qty_on_hand`, so reserved stock is still physically there and `stock_available` is what is free to sell. Posting a **delivery** is the only thing that takes stock out, at the weighted average, releasing that cost to COGS. Posting a **sales invoice** earns the revenue and creates the debt, and moves no goods. Collapsing any two of these is how stock and revenue drift apart. The sales order itself is a `deals` row with `direction = 'receiving'`, the mirror of the purchase order.
- A customer **credit note** always reduces the sale and the receivable; only lines marked `restock` go back on the shelf, at the cost they left on, so damaged returns are credited but written off. A note posts one journal or two. `customer_open_items.outstanding` subtracts **both** payments and posted credit notes — an early version subtracted only payments, so a credited invoice still read as owed in full and the credit check refused orders against money the customer no longer owed (caught 2026-11-01; spec page 8 is the test: 500, collect 200, credit 50, remaining 250).
- **Phase 4 keeps two payment paths apart on purpose.** The existing **Add payment / Fully paid** box inserts without a status, so the column default makes it `legacy`: it stays out of the ledger and `deal_summary` still counts it, so "left to pay" drops the moment it is recorded, exactly as before. The new receipts/payments screens create a `draft` and run `preview_payment()` → `post_payment()`, which is the flow spec page 26 draws. The RLS insert policy therefore admits **both** `legacy` and `draft`; narrowing it to `draft` alone makes every payment the current app records fail RLS — that was caught before applying, on 2026-11-02. A client can never insert a `posted` row.
- **An unallocated supplier payment posts as an advance; an allocated one now clears payables.** Until 2026-11-07 there was no posted supplier bill, so every supplier payment went `Dr 1400 / Cr bank` and an allocation was refused outright. Phase 2's `PIN` credits 2100, so both sides now behave the same way: the allocated share settles through `post_settlement()` (`Dr 2100`, carrying the exchange difference, the only part with a bill behind it) and the unallocated remainder is still an advance — `Dr 1400` for a supplier, `Cr 2200` for a customer. The rule that replaced the blanket refusal is in `private.payment_plan()`: **an allocation has to name a posted bill on the payment's own order** — a `PIN` for a supplier, a sales invoice for a customer — or posting is refused, because a settlement would otherwise clear a payable that was never posted. `apply_supplier_advance` (Dr 2100 / Cr 1400) is no longer a waiting template; `post_advance_application()` calls it.
- **The receipt / payment screen saves a draft before it previews or posts.** `moneyDialog` writes the draft first because `preview_payment` and `post_payment` both take a payment id and read the saved row — previewing figures that only exist on screen would let the preview and the posting drift apart, which is the whole thing `payment_plan` exists to prevent. Posting is armed by a **second click on the button**, not a confirmation box: `openModal` calls `closeModal` first, so a confirm would destroy the dialog and everything typed into it. Any edit disarms it and clears the previewed journal, because neither should outlive the numbers it was based on. The bank dropdown offers **base-currency accounts only** (`payment_plan` refuses the rest until phase 6 revaluation), and an **empty rate box means "use the rate on file"**, not a rate of zero — so a rate is only demanded when none is on file, and the readout shows the figure the database will actually resolve.
- **`#view` is refilled on every render but never replaced, so click handlers must not be added with `addEventListener`.** `onView(handler)` keeps one handler slot and removes the previous one. Before it, each visit to a page added another listener to the same element: visiting an order twice made one click run the handler twice, against a stale copy of the record it closed over. Harmless for a reload, not at all harmless once a button posts a payment.
- **An order's payments card carries both paths at once and must keep saying which is which.** Legacy rows show "Not in the ledger" and keep their plain delete; a draft gets Edit / Post / ✕; a posted one gets Reverse (owner only) and *never* a delete, because the RLS policy would refuse it and an UPDATE or DELETE that fails `using` affects zero rows rather than raising — the button would silently appear to do nothing. The two account columns read "—" for a draft or a reversed row, so they agree with `deal_summary`, which counts legacy and posted only.
- **`private.payment_plan()` is the single source of a payment's arithmetic**, read by both `preview_payment()` and `post_payment()`, so a previewed journal and a posted one cannot drift. It is `stable` and issues **no** document number: a preview that burned a `PAY-` code would leave a permanent hole each time one was opened and abandoned — the same reason `peek_party_code()` exists beside `next_party_code()`.
- **`supplier_open_items` / `ap_aging` read the matched bill where there is one, and the ORDER where there is not — and `bill_source` says which.** Since 2026-11-07 the view is a `union all`: a posted `PIN` gives an `'invoice'` row whose outstanding is the bill less payments, less posted supplier returns, less applied advances; an order with **no** posted `PIN` still gives an `'order'` row from `deal_summary`, because those are real commitments the owner has to see on Payables and all the live data is of that kind. The two sets cannot overlap — an order appears as an order row only while no posted `PIN` names it — so nothing is double-counted. `ap_aging` counts the order rows separately as `unmatched_orders`. Returns are receipt-scoped rather than invoice-scoped, so they reduce the bill on their *order*; with one bill per order (the rule `supplier_invoices.deal_id` keeps) that is the same thing.
- **A supplier bill clears an accrual; it never adds stock a second time.** This company is on the receipt-before-invoice path (spec page 9), so `post_goods_receipt` debits 1300 and credits 2110, and the bill then clears 2110 and credits 2100 — it moves no goods and touches no quantity, only `qty_invoiced`. `post_supplier_invoice()` therefore **refuses a bill with no posted goods receipt behind it**, because there would be no accrual and posting would have to value goods that have not arrived (that is the transit path, a different set of templates). The only way a bill changes stock cost is when it *disagrees* with the accrual, and that difference posts through its own approved template. The `goods_in_transit` / `receive_from_transit` templates stay on file, unused, for a company that later picks that path. Spec page 9: "These are alternative posting paths; do not post all of them for the same goods."
- **`private.accrual_open()` reads the LEDGER, not the documents, and counts `status in ('posted','reversed')`.** Recomputing from receipts would fold freight into the accrual, because `post_landed_cost` rewrites a receipt line's `unit_cost` while landed cost credits 2100, not 2110 — and the ledger is the thing the bill actually has to clear. The status filter is the same trap this schema keeps re-making: filtering to `'posted'` alone would drop a cancelled receipt's original journal and leave its mirror standing, so the accrual would read **negative** and a bill against it would post the whole amount as a price difference straight into stock.
- **`private.invoice_plan()` is the single source of a bill's arithmetic**, read by both `preview_supplier_invoice()` and `post_supplier_invoice()`, exactly as `payment_plan` is for a payment — it is `stable` and issues **no** document number, so an abandoned preview cannot burn a `PIN-` code. It is also what splits the bill: the base value clears the open accrual first, anything above that is a price difference, and a bill marked `is_final` writes any residual accrual back against stock cost. Posted in **base currency on purpose** — the split has to land exactly, and proportionally splitting a foreign amount would re-round and drift; the original currency, rate and foreign total stay on the row for the aging reports.
- **A price difference blends into the units still HELD, not the ones already sold.** `private.blend_invoice_difference()` spreads the gap over the bill's lines and into `item_costs.avg_cost`, the same shape `post_landed_cost` uses, with the rounding crumbs on the last line so the total lands exactly. Units already sold keep the cost they left on, because spec page 6 is explicit that an old posted cost is never silently rewritten — which also means cancelling the bill unwinds the blend only as far as the stock is still there.
- **Shipment-to-PO allocation is its own table; `shipments.items` is untouched.** Spec page 5 needs "one PO across several shipments and several POs in one shipment", a many-to-many link that a jsonb column on the shipment cannot express — so `shipment_allocations` keys on the **order line**, while `shipments.deal_id` keeps meaning "the order this shipment was raised against" (what the existing Record shipment screens read) and the jsonb blob keeps feeding that untouched flow. `allocate_shipment()` **replaces** a shipment's whole allocation rather than adding to it, because the screen shows the full list and saving it should leave exactly what is on screen — a dropped line has to give its quantity back, so the function recomputes `qty_shipped` over the union of old and new lines and refuses to ship more than was ordered across *every* shipment. The RLS write policy admits the **owner only**: a direct client write would go around that check, so the client is given the function instead.
- **A supplier return leaves at the cost it arrived at.** `post_supplier_return()` reads the receipt line's `unit_cost`, not the current average, and unwinds the weighted average the same way `cancel_goods_receipt` does, so the remaining average is undisturbed. It refuses to send back more than was accepted (counting earlier posted returns) or more than is still on hand. `settlement` is `'credit'` or `'refund'` and both post identically — `Dr 2100 / Cr 1300`; money actually coming back is a separate bank transaction.
- **An advance application is its own document, not a flag on the payment.** `journals_source_event_uq` means one `(source_table, source_id, event)` posts once, so hanging the event off the party row would let each party apply an advance exactly once, ever. `post_advance_application()` checks the advance against what the ledger says is **held** (`private.advance_held()`, `'posted','reversed'` again) and against what the bill it points at still owes, and the table's own check constraints stop a supplier application pointing at a sales invoice or at both at once.
- The 13 event templates from spec page 9 are rows in `posting_templates`, not code, because the spec requires an accountant to validate the event-to-account mapping before real posting — `select * from posting_templates` is that review. Changing one re-routes every future journal, so it is owner-write only. Spec page 9 also says returns need their own approved templates, so `sales_credit_note` (Dr 4000 / Cr 1200) and `return_to_stock` (Dr 1300 / Cr 5000) were added as rows the same way, bringing it to 15. Phase 2 added three more on 2026-11-07 — `invoice_price_difference` (Dr 1300 / Cr 2100), `invoice_price_credit` (Dr 2110 / Cr 1300) and `supplier_return` (Dr 2100 / Cr 1300) — which spec page 9 demands for "tax, returns, shortages and price differences", bringing it to **18**.
- `fx_rate_for()` raises when no rate is on file rather than assuming 1:1, which would silently misstate every foreign balance. Rates are stored base-per-1-foreign (KWD per 1 USD), and `to_base()` rounds through `currency_decimals()` so KWD keeps 3 decimals.
- Existing deals and payments carry `status = 'legacy'`: they were never journal-posted, and marking them `posted` would make the trial balance claim entries that do not exist. Opening stock was deliberately absent until phase 6 — per spec page 3 it needs an approved opening transaction, which `post_opening_balance()` now is.
- **An opening balance is a document that posts a journal, never a number typed onto a party or an item.** That is spec page 3 ("do not type an unexplained number into the master"), and it is why `parties` and `items` have no `opening_balance` column: the figure every later report is measured from has to be reviewable, reversible and dated. `opening_balances` + `opening_balance_lines` carry four kinds of line — `stock`, `customer_invoice`, `supplier_invoice`, `bank` — and `post_opening_balance()` writes **one** multi-line journal with everything contra'd against **3100 Opening balance**, its own equity account rather than 3000, so carried-over data stays separable from real equity for ever. Owner-only, and a partial unique index on `(company_id) where status = 'posted'` means opening data imports **once**: a correction is `cancel_opening_balance()` and a re-import, not a top-up, because "no transactions = zero balance" leaves nothing to add to.
- **Opening unpaid invoices hang off a hidden synthetic order, one per account.** Everything in this schema hangs off a `deals` row — `sales_invoices.deal_id` and `supplier_invoices.deal_id` are both not-null, and `private.payment_plan()` reads a payment's deal for its currency and party — but a carried-over invoice has no order behind it. So `private.opening_deal()` makes one `deals` row per account per direction, `reference = 'OPENING'`, `status = 'legacy'` (which means exactly "predates the ledger"), and in exchange *every existing screen keeps working untouched*: the aging reports, the open-items views, the party statement, and collecting or paying an opening invoice through the ordinary receipt / payment screens. The two alternatives were rejected on purpose — a nullable `deal_id` would leave opening invoices uncollectable until `payment_plan` was reworked, and a ledger-only opening balance would keep the trial balance right but never show an opening invoice in an aging report or let one be settled on its own. Decided with the owner 2026-11-07. `open_orders` therefore excludes `reference = 'OPENING'`: the supplier side needs a `deal_items` row (because `supplier_invoice_lines.deal_item_id` is not-null) and without the filter those would read as orders with goods still to come, which they are not — the opening *bill* is what is outstanding, and `supplier_open_items` already reports it through its invoice branch.
- An opening invoice is a **real posted invoice row**, flagged `is_opening`, carrying one line for the whole amount — `customer_open_items` derives the amount from the lines, so a line-less invoice would read as zero outstanding and never appear in an aging report. Opening stock blends into `item_costs` exactly as a goods receipt does, so the first real receipt after launch averages against it correctly. Cancelling marks the created invoices `cancelled` rather than deleting them (the open-items views filter `status = 'posted'`, so that removes them from every balance while keeping the trail), takes the stock back out at the cost it came in at, and refuses outright while a posted payment is still allocated to one of them.
- **There is deliberately no `posting_templates` row for `opening_balance`.** The 18 templates each map one event to one debit and one credit account, which is what spec page 9 asks an accountant to validate. An opening entry is not a pair — it debits stock, receivables and the bank and credits payables, all against one contra — so a row would misrepresent it. What the accountant reviews instead is account 3100 and the document itself, which is why the document exists and carries its own `OPN-` number.
- **The phase 6 reports all read `general_ledger`, never `journal_lines` directly**, because the view already filters `status in ('posted','reversed')` — the mistake this schema keeps re-making. Reading the view inherits the correct filter instead of restating it and getting it wrong. `shipment_cost` takes a receipt's goods value from the **2110 accrual in the ledger**, not from `goods_receipt_lines.unit_cost`, because `post_landed_cost` rewrites that unit cost to include freight while crediting 2100 — reading the line would count freight twice. And `profit_and_loss()` / `balance_sheet()` are deliberately **not** `security definer`: a function defaults to invoker, so RLS still applies, and making a reporting function definer would hand the whole ledger to anyone holding the publishable key — the same hole `security_invoker = true` on views exists to close.

## Working notes
- Keep UI edits inside `public/`; keep the three logo PNG filenames and transparent backgrounds. Schema work goes in `supabase/migrations/`, applied under the same name and committed in the same change — never edit a migration that has already been applied, add another.
- RLS is the whole security boundary: the browser holds only the publishable key, which is public in `CONFIG`. Every new table needs its policies in the same migration that creates it, or it is readable by anyone with that key. New Supabase tables have RLS *off* by default.
- **Every view needs `security_invoker = true`**, set in the migration that creates it. Without it the view reads its base tables with the view *owner's* rights, RLS never runs, and the view is readable by anyone holding the publishable key — the table's own policies do not save it. This was a real hole, caught 2026-10-29: the four views added by the ERP work (`activity_log`, `general_ledger`, `order_progress`, `stock_on_hand`) all lacked it, and `order_progress` served all 19 purchase lines to an anonymous caller. Three read empty at the time, so nothing looked wrong; `general_ledger` would have gone public with the first posted journal. The query to check for regressions is in `supabase/migrations/README.md`.
- Don't paste real passwords or the service-role key into chat or files; only the publishable key belongs in `CONFIG`.
- The README tells the owner to change any password they previously typed into a chat window.
